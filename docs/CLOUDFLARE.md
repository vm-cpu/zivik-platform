# НаСвітло на Cloudflare: Astro + EmDash

Друга збірка сайту — на Cloudflare Workers, з адмінкою
[EmDash](https://github.com/emdash-cms/emdash) і контентом у D1. Поки що вона
живе **поруч** із Next (Vercel), а не замість нього: обидві збірки рендерять ті
самі компоненти, стилі й дані, тож усе, що змінюється на `main`, потрапляє в
обидві. Перемикання — окремий крок наприкінці (див. «Перемикання»).

## Як це влаштовано

```
EmDash admin (/_emdash/admin)  ──publish──▶  deploy hook  ──▶  Workers Builds
        │                                                         │
        ▼                                                         ▼
   D1 «nasvitlo»  ◀── cf:pull (опубліковане) ── npm run cf:build ── astro build
                                                                  │
                                              статичні сторінки + Worker (адмінка)
```

1. **Редактори** працюють в адмінці EmDash. Чернетка нікуди не йде; публікація
   (а також зняття з публікації, видалення, відновлення) викликає перезбірку
   сайту через deploy hook — `site/emdash/rebuild-on-publish.ts`.
2. **Збірка** (`npm run cf:build`) знімає з D1 *опублікований* контент
   (`scripts/cf/pull.mts` → `.emdash/snapshot.json`) і компілює його замість
   літералів у `src/content/*.ts` (`site/content/vite-plugin.mjs`). Замінюється
   лише ініціалізатор однієї `export const` у кожному модулі — похідні
   значення, функції й **перевірки** модуля лишаються і працюють на даних з CMS.
3. **Усі публічні сторінки пререндеряться** під час збірки. Тому правка, яка
   суперечить сама собі (наприклад, `summarySlug` на неіснуючий огляд), валить
   *збірку* з тим самим повідомленням, що й у коді, і сайт лишається на
   попередній версії. На Worker працюють лише адмінка EmDash, редірект `/` →
   `/uk|/en` і 404.
4. Після публікації правка на сайті — за час збірки (~1–2 хв).

### Що з Next перевикористано і як

| Що | Як |
|---|---|
| Сторінки `src/app/[locale]/**/page.tsx` | Маршрути в `site/pages` викликають модулі сторінок Next напряму (`site/lib/route.ts`): ті самі `generateStaticParams`, `generateMetadata`, `notFound()`. |
| Метадані (`lib/seo.ts`) | `site/lib/metadata.ts` перетворює `Metadata` Next у теги `<head>` з тими ж правилами злиття. |
| `"use client"`-компоненти | Острови: `site/islands/`. Гідратується рівно той набір компонентів, що й у Next; кожен острів рендериться окремим коренем з тим самим `identifierPrefix`, що й у браузері (інакше `useId` розходиться). |
| `next/link`, `next/navigation`, `next/image` | Шими в `site/shims/`. |
| `next/font` | `@fontsource` з тими самими накресленнями (`site/styles/fonts.css`). |
| Заголовки безпеки | Спільний `src/lib/security-headers.ts`: Next бере з нього `headers()`, Cloudflare — файл `_headers` (+ HSTS, який Vercel додавав сам). |
| `robots.txt`, `sitemap.xml`, `search-index.json` | Ті самі функції з `src/app`, серіалізовані в `site/pages/*.ts`. |

Перевірено: усі 84 згенеровані файли (сторінки, sitemap, robots, індекс пошуку), зібрані зі знімка D1, байт-у-байт
збігається зі збіркою з файлів; скриншоти Next і Astro (1280 і 390 px) — ті самі
висоти сторінок, без помилок гідратації.

## Контент у CMS

Опис колекцій — `site/content/collections.ts`. Двомовні поля (`Localized`)
стали парами `назва_uk` / `назва_en` в одному записі: вбудована i18n EmDash
(рядок на мову) зробила б кожен факт — суму, рік, статус — редагованим двічі і
забрала б префікс `/uk`.

| Колекція | Звідки | Примітка |
|---|---|---|
| Провадження (`cases`) | `cases.ts` → `registryCases` | Усі поля реєстру. |
| Інституції | `institutions.ts` | |
| Огляди рішень (`summaries`) | `summaries/index.ts` → `SUMMARIES` | Див. нижче. |
| Мапа: події / суди / країни | `map.ts` | Масиви (`courts`, `seats`…) — JSON-поля. |
| Команда, Партнери, Про проєкт | `team.ts`, `partners.ts`, `about.ts` | Фото й логотипи — шляхи в `/public`. |

**Огляд рішення в адмінці** розкладено на поля: шапка, «коротко і чому
важливо», джерело рішення, форум — звичайні поля (пари UA/EN). Текст огляду
(англійський оригінал і український) — повторювач, рядок на абзац: тип
(`lead`, `h2`, `p`, `dispositif`…), текст, назва в змісті. Так само рядками
редагуються цифри, «коротко про справу», хто є хто, хронологія, висновки,
тлумачення, тимчасові заходи, глосарій, FAQ, інструменти, пов'язані справи і
джерела. Розділи, де список вкладений у список (ордери, заперечення, суми,
втрати, ланцюг відповідальності, «що було далі», театри на мапі), лишаються
JSON — але кожен окремим полем: повторювач EmDash не вміщує інший повторювач.

Поле «рядок або UA/EN» (наприклад, цифра «298»): якщо EN порожнє, значення
однакове для обох мов.

Поза CMS (лишаються в коді): тексти інтерфейсу (`src/i18n/dictionaries`),
правові сторінки (`legal.ts` — у текст вшиті лічильники з реєстру), глосарій і
статистика (вони *похідні* від оглядів і реєстру, тож оновлюються самі).

Порядок записів на сайті задає службове поле «Позиція в списку».

### Гарантія, що нічого не губиться

`npm run cf:content -- check` проганяє кожен запис кожної колекції через
«файл → рядок EmDash → значення» і вимагає глибокої рівності з оригіналом. Він
є в CI. Якщо в тип у `src/content/types.ts` додати поле й не описати його в
`collections.ts`, перевірка впаде, і поле не зникне тихо.

## Команди

| Команда | Що робить |
|---|---|
| `npm run cf:dev` | Локально: Astro + EmDash + локальна D1/R2 (miniflare). Адмінка — `http://localhost:4321/_emdash/admin`; швидкий вхід — `/_emdash/api/setup/dev-bypass`. |
| `npm run cf:build` | Повна продакшн-збірка: check → seed → pull (з віддаленої D1) → `astro build`. |
| `npm run cf:build:local` | Те саме, але знімок — з локальної D1. |
| `npm run cf:preview` | Запуск зібраного сайту у workerd. |
| `npm run cf:deploy` | `cf:build` + `wrangler deploy` (потрібен `CLOUDFLARE_API_TOKEN`). |
| `npm run cf:content -- check` | Round-trip перевірка (див. вище). |
| `npm run cf:content -- seed` | `.emdash/seed.json` зі схемою і поточним контентом файлів. |
| `npm run cf:content -- push [--yes]` | Перехідний період: доносить правки з файлів у запущену EmDash (див. нижче). |
| `npm run cf:check` | Типи `site/`. |

## Перший запуск на Cloudflare (акаунт Vm@bot-partners.com)

Уже зроблено: D1 `nasvitlo` (EEUR, id у `wrangler.jsonc`).

1. **Увімкнути R2** у дашборді (R2 Object Storage → Enable; безкоштовний тариф,
   але Cloudflare просить підтвердити спосіб оплати). Потім створити бакет
   `nasvitlo-media`. Без R2 Worker не задеплоїться — у ньому медіатека EmDash.

   **Тариф Workers.** Worker важить ~2,4 МБ gzip — у межах безкоштовного
   ліміту 3 МБ, бо адмінку зібрано лише з українською й англійською
   (`site/emdash/admin-locales.mjs`; усі 29 мов EmDash додавали 1,65 МБ).
   Інше обмеження безкоштовного тарифу — 10 мс процесорного часу на запит:
   публічних сторінок воно не стосується (це статика), але важкі дії адмінки
   (публікація з ревізіями й пошуковим індексом) можуть його перевищувати.
   Якщо в адмінці з'являться помилки 1102 / «exceeded CPU», потрібен Workers
   Paid ($5/міс).
2. **Підключити репозиторій** (Workers & Pages → Create → Import a repository →
   `vm-cpu/zivik-platform`):
   - Build command: `npm run cf:build`
   - Deploy command: `npx wrangler deploy`
   - Production branch: поки гілка цього PR; після злиття — `main`.
   - Змінні збірки: `NEXT_PUBLIC_SITE_URL` = адреса сайту на Cloudflare
     (канонічні URL, sitemap); `SITE_INDEXABLE` / `FEATURE_GLOSSARY` — як на
     Vercel.
3. Перша збірка піде з файлів (база ще порожня — `cf:pull` так і скаже).
4. Відкрити `https://<адреса>/_emdash/admin`, пройти налаштування (перший
   користувач — адміністратор, вхід через passkey) і **погодитися імпортувати
   вміст сайту** — це контент із файлів на момент збірки.
5. **Deploy hook**: Worker → Settings → Builds → Deploy Hooks → створити для
   production-гілки; URL записати секретом Worker-а:
   `npx wrangler secret put DEPLOY_HOOK_URL` (або в дашборді, Settings →
   Variables and Secrets, тип Secret).
6. Перевірити: змінити щось в адмінці → «Опублікувати» → у Builds з'являється
   збірка від deploy hook → правка на сайті.

## Перехідний період

Доки Next на Vercel — основний сайт, **джерело правди — файли в
`src/content`**, і правки контенту робляться там, як і раніше. CMS тримає копію.
Щоб донести свіжі правки з `main` в адмінку:

```sh
EMDASH_URL=https://<адреса> EMDASH_TOKEN=<токен> npm run cf:content -- push        # показати різницю
EMDASH_URL=https://<адреса> EMDASH_TOKEN=<токен> npm run cf:content -- push --yes  # записати й опублікувати
```

Токен — в адмінці (Settings → API tokens, права content read/write). `push`
**перезаписує** правки, зроблені в адмінці, тому без `--yes` лише звітує, а
записи, яких немає у файлах, ніколи не видаляє.

Зміна **схеми** (нове поле в типі): описати його в `collections.ts` і додати
поле в адмінці (Content types) з тим самим slug — або, поки даних в адмінці
немає чого берегти, перестворити базу з сіду.

## Перемикання (коли будете готові)

1. Заморозити правки контенту у файлах; `push --yes` востаннє.
2. Перевести домен на Worker (Settings → Domains & Routes).
3. З цього моменту контент редагується **лише** в адмінці. `push` більше не
   запускати.
4. Прибирання в коді (окремим PR): літерали з `src/content/*.ts` → дані з
   CMS; `src/app` → `site/pages` (з'єднати `site/lib/route.ts` зі сторінками);
   прибрати Next, `vercel.json`, шими.

## Відомі обмеження і наступні кроки

- **`scripts/data-check.mjs` читає файли як текст**, тож правки з адмінки він не
  бачить. Інваріанти всередині модулів (`summaries/index.ts`, `about.ts`…)
  спрацьовують під час пререндеру, але решту правил data-check варто перевести
  на значення і запускати на знімку в `cf:build`.
- **Вісім розділів огляду — JSON** (ордери, заперечення, суми тощо; див.
  вище). Їх можна розкласти далі, коли EmDash дозволить вкладені повторювачі,
  або винести елементи в окремі колекції з посиланнями.
- **Фото й логотипи — рядки-шляхи**, а не медіа EmDash. Після ввімкнення R2 —
  перевести на поля `image` з завантаженням.
- **404 лише українською** (`404.html` з українською шапкою). Next показував
  шапку мовою розділу.
- Коментарі-обґрунтування в `src/content/*.ts` (чому саме таке значення) у
  CMS не переносяться; при перемиканні їх варто зберегти (наприклад, полем
  «Редакторська примітка»).
